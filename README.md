Они описывают семь объектов из учебных проектов по сборке заказов и маркетинговой атрибуции. Все исходные бизнес-данные синтетические. Автоматический стенд с каталогом и обоими источниками запущен один раз 19 ноября 2026 года в GitHub Codespaces: код возврата 0, прошли 12 из 12 проверок (раздел [Стенд](#стенд), [протокол прогона](docs/runs/2026-11-19-stand.md)).

| ClickHouse, база `marketing_jan` | `events`, `spend`, `attribution`, `channel_metrics`, `user_funnel` | События, расходы по каналам, распределение подписок, канальная витрина и воронка |

Имена сверены с DDL двух соседних учебных проектов. Заказы — проект сборки заказов `metabase-order-picking` (P17, коммит `d21a222`), файл `sql/postgres/001_orders.sql` в его репозитории. ## Запуск с каталогом

1. Подготовьте доступные из процесса ingestion экземпляр OpenMetadata 2.0.8, базу P17 и сохранённый снимок P16. Для P16 используйте имя базы `marketing_jan`. Порядок загрузки данных описан в `README.md` проектов `metabase-order-picking` и `marketing-funnel-datalens`.
2. Для источников задайте учётные данные с правами чтения схем. Для каталога задайте адрес API с окончанием `/api` и JWT бота ingestion. Экспортируйте в окружение переменные для выбранного источника и каталога. Имена и примеры адресов приведены в [.env.example](.env.example). Адреса должны разрешаться из среды, в которой работает CLI.
3. В окружении Python 3.11 с клиентом и драйверами выполните нужную команду из корня проекта. Первый запуск создаёт или обновляет метаданные сервисов `p17_picking` и `p16_marketing` в указанном каталоге.

```text
python -m pip install "openmetadata-ingestion[postgres,clickhouse]==2.0.8.0"
metadata ingest -c workflows/postgres.yaml
metadata ingest -c workflows/clickhouse.yaml
```

4. В каталоге проверьте имена объектов по таблице выше и тип `View` у `order_facts`. Повторите сбор и сравните набор имён и введённые вручную описания. Фильтры ограничены перечисленными объектами. Для этих частичных выборок выключены перезапись описаний и пометка исчезнувших объектов как удалённых. [PostgreSQL](workflows/postgres.yaml) · [ClickHouse](workflows/clickhouse.yaml)

## Владельцы, глоссарий и происхождение данных

После первого сбора создайте две учебные группы, глоссарий `LabMetrics` и семь терминов. Элементы `teams`, объект `glossary` и элементы `terms` по отдельности соответствуют моделям запросов OpenMetadata. Раздел `objects` задаёт назначения по полному имени каждой таблицы (FQN). Для PostgreSQL это `p17_picking.picking.picking.<таблица>`, для ClickHouse — `p16_marketing.default.marketing_jan.<таблица>`. Этот вид подтвердил прогон стенда: коннектор ClickHouse ставит на место базы `default`, а `marketing_jan` делает схемой ([протокол](docs/runs/2026-11-19-stand.md#допущения-которые-проверил-прогон)). Перенесите в карточку её описание, назначьте указанную группу, подтвердите термин и добавьте входящие связи из `upstream`. Группы и назначения подготовлены для учебного проекта. На стенде всё это по REST применяет [scripts/apply_catalog.py](scripts/apply_catalog.py). [Спецификация](catalog.json)

В PostgreSQL представление `order_facts` читает `orders`. В ClickHouse `attribution` и `user_funnel` читают `events`, а `channel_metrics` использует сразу три источника — `events`, `spend` и `attribution`. Всего в спецификации шесть прямых связей. Они выписаны вручную из SQL соседних проектов: представление заказов — `metabase-order-picking`, файл `sql/postgres/001_orders.sql`; атрибуция, воронка и канальная витрина — `marketing-funnel-datalens`, файлы `sql/clickhouse/attribution.sql`, `sql/clickhouse/user_funnel.sql` и `sql/clickhouse/channel_metrics.sql`.

Чтобы связать термин с полем, откройте схему таблицы в её карточке. Для каждого поля из `column_terms` назначьте указанный термин `LabMetrics` на строке столбца. Например, `PickingOrder` относится к идентификатору заказа в таблице и представлении, а `PickingDuration` — к `order_facts.pick_seconds`. В двух источниках предусмотрено девять таких назначений. [Список по таблицам](catalog.json)

## Отчёт о полноте карточек

Из корня проекта запустите команду на синтетическом примере. Достаточно стандартной библиотеки Python.

```text
python scripts/completeness.py examples/partial-tables.json
```

Знаменатель каждого показателя — семь ожидаемых объектов. В примере есть три действующие карточки. У двух заполнено описание, у двух назначена ожидаемая команда и у одной подтверждён указанный термин. Всем трём условиям отвечает карточка `orders`. Поле `objects` показывает пробелы по каждой таблице, включая отсутствующие и удалённые карточки. [Пример снимка](examples/partial-tables.json)

Для измерения на стенде запросите каждый из семи объектов через `GET /api/v1/tables/name/<FQN>?fields=owners,tags,columns&include=all` и сохраните найденные объекты в одном JSON-массиве. У записи с `deleted: true` отчёт покажет `deleted`. Подтверждённое отсутствие карточки (HTTP 404 при достаточных правах) оставляет её за пределами массива. При ошибке доступа или связи завершите выгрузку после восстановления доступа. Если используете список таблиц, соберите элементы `data` со всех страниц с теми же полями до конца пагинации. Передайте путь к готовому массиву вместо пути к примеру.

Для сверки столбцов до и после повторного сбора выполните команду для каждой выгрузки.

```text
python scripts/completeness.py --columns examples/partial-tables.json
```

В разделе `column_terms` числитель — количество столбцов с ожидаемым термином из глоссария в состоянии `Confirmed`, знаменатель — девять назначений. На примере подтверждены оба поля `order_id` (2 из 9). У `pick_seconds` термин пока предложен. Если выгрузка опустила массив столбцов или их метки, отчёт укажет `columns_unavailable` или `tags_unavailable`. Для сверки такого поля потребуется выгрузка с этими данными. ## Проверки качества данных

После сбора откройте карточки `orders` и `attribution` и сверьте их полные имена с конфигурациями ниже. Для запуска бот должен иметь доступ к подключениям и право записывать тесты и их результаты. Учётным записям источников нужно право `SELECT` на проверяемые таблицы. Из окружения ingestion выполните обе команды.

```text
metadata test -c workflows/quality-orders.yaml
metadata test -c workflows/quality-attribution.yaml
```

| Карточка и проверка | Что считает SQL |
|---|---|
| `orders` · `order_quantities` | Заказы с пропуском в одном из трёх количеств или нарушением условий `requested > 0` и `0 ≤ errors ≤ picked ≤ requested` |
| `attribution` · `credit_sum` | Пары «конверсия, модель», в которых хотя бы один вес выходит за интервал (0, 1] или не является конечным числом, либо сумма весов, вычисленная в Float64, отклоняется от единицы больше чем на 10⁻⁹ + 10⁻¹² (запас 10⁻¹² — на округление: границы 1 ± 10⁻⁹ включены) |

В обоих случаях ожидается ноль нарушений. Обе проверки задают `strategy: COUNT`, `operator: '<='` и `threshold: '0'`. При `strategy: COUNT` проверка `tableCustomSQLQuery` сравнивает с порогом число, которое вернул запрос (`count(*)`), а не количество строк результата. Это подтвердил прогон стенда. Запрос всегда возвращает одну строку, но на чистых данных обе проверки получили `resultRowCount` = 0 и `Success`. С одной испорченной группой `credit_sum` получила 1 и `Failed`. [Протокол](docs/runs/2026-11-19-stand.md#допущения-которые-проверил-прогон) Проверьте в карточках результат последнего запуска и значение `resultRowCount`. Повторный запуск обновляет одноимённую проверку из YAML. Для пустой таблицы оба запроса возвращают ноль. Правило атрибуции учитывает только пары, представленные в таблице. Как запустить. Нужен Linux с Docker Compose v2.1.1 или новее, Python 3.10+ и curl. По умолчанию скрипт требует не меньше 15 ГБ свободного диска для Docker и 6 ГБ памяти; порогами управляют `MIN_FREE_DISK_GB` и `MIN_MEMORY_GB`. В документации OpenMetadata для локального Docker указан минимум 6 GiB памяти и 4 vCPU. В прогоне 19.11 загрузка образов заняла 1 мин 38 с, подъём стенда — 2 мин 2 с, установка клиента — 1 мин 36 с. Вход, оба сбора, применение каталога, проверки качества и итоговая сверка заняли 67 с. Из корня репозитория:

```text
bash stand/run.sh
```

Скрипт проверяет ресурсы и создаёт `stand/.env` со случайными паролями. Затем он поднимает стенд (`docker compose up -d --wait`), входит администратором и получает токен бота `ingestion-bot`. После этого собирает метаданные обоих источников и выгружает карточки. Если какого-то из семи объектов `catalog.json` нет или он помечен удалённым, скрипт останавливается на шаге 8 (`completeness.py --require-present`, код 4) до первой записи в каталог; список пропавших FQN — в выводе шага, подробности — в `before_completeness.json`. Затем скрипт дважды применяет каталог и выгружает карточки (`applied_*`). Перед повторным сбором он ставит в источниках комментарии с меткой времени прогона: к одному столбцу каждого из семи объектов и к самой таблице. Потом повторяет сбор и снова выгружает карточки (`after_*`). В конце запускает обе проверки качества и отрицательный контроль: в `attribution` добавляется группа `negative_control` с суммой весов 0,5, и `credit_sum` должен упасть. Сразу после этого строка удаляется синхронной мутацией (`ALTER TABLE … DELETE`, `mutations_sync=2`), а скрипт проверяет, что таких строк не осталось (`negative-cleanup.txt`). То же удаление выполняется в начале шага проверок качества, на случай если прошлый прогон с `KEEP_STAND=1` остановился между вставкой и удалением. Затем идёт итоговая сверка. Стенд удаляется в конце (`docker compose down -v`), даже при ошибке; оставить его можно через `KEEP_STAND=1`. Комментарии в источниках после прогона остаются; следующий прогон ставит свои, с новой меткой времени. Полностью чистое состояние источников даёт только `docker compose down -v`. Пароли и токены в вывод не попадают, а в файлах `stand/out/` заменяются на `[REDACTED]`. Замена идёт по значению, поэтому стандартный пароль администратора `admin` превращает в `[REDACTED]` и одноимённый логин (раздел «Ограничения»).

## Ограничения

- Прогон стенда один, на одной машине GitHub Codespaces. Повторяемость и время на другой машине не измерялись.
- Интерфейс OpenMetadata в прогоне глазами не открывался, снимков страниц нет. Карточки, связи и результаты проверок прочитаны через REST API.
- Пиковая память не измерена: `docker-stats.txt` — один снимок в конце прогона, без процесса CLI.
- Связи происхождения добавлены по спецификации через API. Автоматическое извлечение связей из SQL (отдельный процесс lineage) не запускалось.
- Дефект выгрузки: `redact()` в `run.sh` заменяет на `[REDACTED]` значения паролей из `stand/.env`. Пароль администратора стенда `admin` совпадает с логином, поэтому `[REDACTED]` стоит и на месте логина `admin` — в названии шага 6, в полях `appliedBy`, `changedBy`, `updatedBy` и в нескольких строках журналов. Секрета там нет. Выгрузка сохранена как есть, `run.sh` не менялся.
- Допуск суммы весов в `credit_sum` задан для вычисленной суммы Float64 с запасом 10⁻¹²: отклонения от 10⁻⁹ до 10⁻⁹ + 10⁻¹² не считаются ошибкой. По оценке, а не по измерению, запас покрывает погрешность сложения при числе весов в группе примерно до тысячи.
- Метка классификатора с тем же FQN, что и термин, сохраняется: `apply_catalog.py` ищет назначение термина по паре `source` и `tagFQN` и добавляет термин глоссария рядом. Допустит ли это сам OpenMetadata, не проверялось.
- Вход администратора, токен бота и пути JSON Patch для владельцев и меток не подтверждены документацией API 2.0.x. На стенде 2.0.8 они сработали; на других версиях не проверялись.
- Образы OpenMetadata скачиваются с Docker Hub (`openmetadata/...`), а не через `docker.getcollate.io`, как в файле релиза. Digest взят из реестра Docker Hub для того же тега. Через `docker.getcollate.io` его проверить не удалось: прокси вернул HTTP 429.
- Версия Docker Engine в devcontainer не закреплена: фича `docker-in-docker` ставит последнюю, в прогоне 19.11 это была 29.9.3. Закреплены базовый образ по digest и версии фич.
- Контейнер ingestion (Airflow) не поднимается, поэтому запуск конвейеров из интерфейса OpenMetadata на стенде недоступен и не проверялся.
- Данные синтетические, объём маленький, команды и термины учебные; права учётных записей проверены только на стенде.
