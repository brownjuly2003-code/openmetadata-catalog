# Каталог учебных данных в OpenMetadata

**Статус — в работе.** Подготовлены два процесса сбора метаданных для OpenMetadata 2.0.8. Они описывают семь объектов из учебных проектов по сборке заказов и маркетинговой атрибуции. Все исходные бизнес-данные синтетические. Для проверки в самом каталоге подготовлен автоматический стенд, но он ещё не запускался (раздел [Стенд](#стенд)).

| Источник | Объекты каталога | Назначение |
|---|---|---|
| PostgreSQL, база и схема `picking` | `orders`, `order_facts` | Заказы и представление с датой создания по UTC, временем ожидания и сборки |
| ClickHouse, база `marketing_jan` | `events`, `spend`, `attribution`, `channel_metrics`, `user_funnel` | События, расходы по каналам, распределение подписок, канальная витрина и воронка |

Имена сверены с DDL двух соседних учебных проектов. Заказы — проект сборки заказов `metabase-order-picking` (P17, коммит `d21a222`), файл `sql/postgres/001_orders.sql` в его репозитории. Маркетинговые таблицы — проект маркетинговой воронки `marketing-funnel-datalens` (P16, коммит `3d60450`), каталог `sql/clickhouse` в его репозитории. В коннекторе ClickHouse физическую базу выбирает поле `databaseSchema`. В PostgreSQL сбор ограничен одной базой и одной схемой, включая представления.

## Запуск с каталогом

1. Подготовьте доступные из процесса ingestion экземпляр OpenMetadata 2.0.8, базу P17 и сохранённый снимок P16. Для P16 используйте имя базы `marketing_jan`. Порядок загрузки данных описан в `README.md` проектов `metabase-order-picking` и `marketing-funnel-datalens`.
2. Для источников задайте учётные данные с правами чтения схем. Для каталога задайте адрес API с окончанием `/api` и JWT бота ingestion. Экспортируйте в окружение переменные для выбранного источника и каталога. Имена и примеры адресов приведены в [.env.example](.env.example). Адреса должны разрешаться из среды, в которой работает CLI.
3. В окружении Python 3.11 с клиентом и драйверами выполните нужную команду из корня проекта. Первый запуск создаёт или обновляет метаданные сервисов `p17_picking` и `p16_marketing` в указанном каталоге.

```text
python -m pip install "openmetadata-ingestion[postgres,clickhouse]==2.0.8.0"
metadata ingest -c workflows/postgres.yaml
metadata ingest -c workflows/clickhouse.yaml
```

4. В каталоге проверьте имена объектов по таблице выше и тип `View` у `order_facts`. Повторите сбор и сравните набор имён и введённые вручную описания. Фильтры ограничены перечисленными объектами. Для этих частичных выборок выключены перезапись описаний и пометка исчезнувших объектов как удалённых. [PostgreSQL](workflows/postgres.yaml) · [ClickHouse](workflows/clickhouse.yaml)

## Владельцы, глоссарий и происхождение данных

После первого сбора создайте две учебные группы, глоссарий `LabMetrics` и семь терминов. Элементы `teams`, объект `glossary` и элементы `terms` по отдельности соответствуют моделям запросов OpenMetadata. Раздел `objects` задаёт назначения по полному имени каждой таблицы (FQN). Для PostgreSQL это `p17_picking.picking.picking.<таблица>`, для ClickHouse — `p16_marketing.default.marketing_jan.<таблица>`. Что коннектор ClickHouse поставит на место базы `default`, а `marketing_jan` сделает схемой, — допущение, проверить на стенде после первого сбора; при другом виде имён нужно поправить `catalog.json` и `workflows/quality-attribution.yaml`. Перенесите в карточку её описание, назначьте указанную группу, подтвердите термин и добавьте входящие связи из `upstream`. Группы и назначения подготовлены для учебного проекта. На стенде всё это по REST применяет [scripts/apply_catalog.py](scripts/apply_catalog.py). [Спецификация](catalog.json)

В PostgreSQL представление `order_facts` читает `orders`. В ClickHouse `attribution` и `user_funnel` читают `events`, а `channel_metrics` использует сразу три источника — `events`, `spend` и `attribution`. Всего в спецификации шесть прямых связей. Они выписаны вручную из SQL соседних проектов: представление заказов — `metabase-order-picking`, файл `sql/postgres/001_orders.sql`; атрибуция, воронка и канальная витрина — `marketing-funnel-datalens`, файлы `sql/clickhouse/attribution.sql`, `sql/clickhouse/user_funnel.sql` и `sql/clickhouse/channel_metrics.sql`.

Чтобы связать термин с полем, откройте схему таблицы в её карточке. Для каждого поля из `column_terms` назначьте указанный термин `LabMetrics` на строке столбца. Например, `PickingOrder` относится к идентификатору заказа в таблице и представлении, а `PickingDuration` — к `order_facts.pick_seconds`. В двух источниках предусмотрено девять таких назначений. [Список по таблицам](catalog.json)

## Отчёт о полноте карточек

Из корня проекта запустите команду на синтетическом примере. Достаточно стандартной библиотеки Python.

```text
python scripts/completeness.py examples/partial-tables.json
```

Знаменатель каждого показателя — семь ожидаемых объектов. В примере есть три действующие карточки. У двух заполнено описание, у двух назначена ожидаемая команда и у одной подтверждён указанный термин. Всем трём условиям отвечает карточка `orders`. Поле `objects` показывает пробелы по каждой таблице, включая отсутствующие и удалённые карточки. [Пример снимка](examples/partial-tables.json)

Для измерения на стенде запросите каждый из семи объектов через `GET /api/v1/tables/name/<FQN>?fields=owners,tags,columns&include=all` и сохраните найденные объекты в одном JSON-массиве. У записи с `deleted: true` отчёт покажет `deleted`. Подтверждённое отсутствие карточки (HTTP 404 при достаточных правах) оставляет её за пределами массива. При ошибке доступа или связи завершите выгрузку после восстановления доступа. Если используете список таблиц, соберите элементы `data` со всех страниц с теми же полями до конца пагинации. Передайте путь к готовому массиву вместо пути к примеру.

Для сверки столбцов до и после повторного сбора выполните команду для каждой выгрузки.

```text
python scripts/completeness.py --columns examples/partial-tables.json
```

В разделе `column_terms` числитель — количество столбцов с ожидаемым термином из глоссария в состоянии `Confirmed`, знаменатель — девять назначений. На примере подтверждены оба поля `order_id` (2 из 9). У `pick_seconds` термин пока предложен. Если выгрузка опустила массив столбцов или их метки, отчёт укажет `columns_unavailable` или `tags_unavailable`. Для сверки такого поля потребуется выгрузка с этими данными. [Снимок](examples/partial-tables.json) · [Проверка на частичной и полной разметке](docs/runs/2026-11-19-columns.md)

## Проверки качества данных

После сбора откройте карточки `orders` и `attribution` и сверьте их полные имена с конфигурациями ниже. Для запуска бот должен иметь доступ к подключениям и право записывать тесты и их результаты. Учётным записям источников нужно право `SELECT` на проверяемые таблицы. Из окружения ingestion выполните обе команды.

```text
metadata test -c workflows/quality-orders.yaml
metadata test -c workflows/quality-attribution.yaml
```

| Карточка и проверка | Что считает SQL |
|---|---|
| `orders` · `order_quantities` | Заказы с пропуском в одном из трёх количеств или нарушением условий `requested > 0` и `0 ≤ errors ≤ picked ≤ requested` |
| `attribution` · `credit_sum` | Пары «конверсия, модель», в которых хотя бы один вес выходит за интервал (0, 1] или не является конечным числом, либо сумма весов, вычисленная в Float64, отклоняется от единицы больше чем на 10⁻⁹ + 10⁻¹² (запас 10⁻¹² — на округление: границы 1 ± 10⁻⁹ включены) |

В обоих случаях ожидается ноль нарушений. Обе проверки задают `strategy: COUNT`, `operator: '<='` и `threshold: '0'`. Что при `strategy: COUNT` проверка `tableCustomSQLQuery` сравнивает с порогом число, которое вернул запрос (`count(*)`), а не количество строк результата, — допущение, проверить на стенде: на данных с ошибками проверка должна упасть. Проверьте в карточках результат последнего запуска и значение `resultRowCount`. Повторный запуск обновляет одноимённую проверку из YAML. Для пустой таблицы оба запроса возвращают ноль. Правило атрибуции учитывает только пары, представленные в таблице. [Заказы](workflows/quality-orders.yaml) · [Атрибуция](workflows/quality-attribution.yaml)

## Проверка конфигураций

Первый тест сверяет состав выборки с таблицами и представлением исходных проектов: фильтры (без учёта регистра, как в OpenMetadata) проверены на контрольном наборе имён, а объекты, которые создаёт DDL стенда и оставляют фильтры, сравниваются с `catalog.json` в обе стороны. Выгрузку настоящего каталога этот тест не заменяет. Второй читает файлы штатным загрузчиком CLI, подставляет тестовые переменные окружения, проверяет типы подключений официальным парсером и запускает фильтры OpenMetadata. Команды и версии зависимостей зафиксированы в [CI](.github/workflows/ci.yml).

Последний полный прогон CI 19 ноября 2026 года (`openmetadata-catalog_20261119-165729`, коммит `21255e1`) прошёл 72 теста: 17 — границы выборки, сравнение с DDL стенда и отчёт полноты, включая назначения на столбцах; 47 — статические проверки файлов стенда и логика применения каталога, выгрузок и итоговой сверки на подменённом API, без контейнеров; 5 — конфигурации, группы и термины в моделях клиента OpenMetadata 2.0.8.0; 3 — SQL проверок качества на контрольных данных, включая границу допуска весов. [Протокол прогона](docs/runs/2026-11-19-second-audit.md#прогоны); прежний прогон с 61 тестом — [stand-prep](docs/runs/2026-11-19-stand-prep.md#прогон-ci-с-этими-тестами).

SQL проверок качества выполнен напрямую в PostgreSQL 16.10 и в `clickhouse-local` 24.8.14.39, без OpenMetadata. На корректных данных оба запроса вернули ноль. ## Стенд

**Стенд подготовлен, но ещё не запускался.** Ни одно утверждение ниже не подтверждено прогоном. Здесь описано, что должен сделать скрипт и по каким признакам оценивать результат.

Что входит:

- [stand/docker-compose.yml](stand/docker-compose.yml) — сервер OpenMetadata 2.0.8, его база PostgreSQL, Elasticsearch и одноразовый контейнер миграций. Образы, переменные и проверки здоровья взяты из файла релиза `docker-compose-postgres.yml` 2.0.8. Копия файла лежит в [stand/upstream](stand/upstream/docker-compose-postgres.yml), а тест сверяет с ней стенд. Отклонения перечислены в начале файла стенда.
- Два источника тех же версий, что уже закреплены в проекте: PostgreSQL 16.10 с заказами P17 и ClickHouse 24.8.14.39 с маркетинговыми таблицами P16. Схемы и синтетические данные скопированы в [stand/fixtures](stand/fixtures/SOURCES.json) с коммитами и контрольными суммами, поэтому стенд не обращается к другим проектам.
- Контейнер ingestion (Airflow) не поднимается: сбор и проверки запускаются внешним CLI `metadata`. На сервере выключен клиент конвейеров (`PIPELINE_SERVICE_CLIENT_ENABLED=false`), так предписывает [документация 2.0.x о внешнем запуске](https://docs.open-metadata.org/v2.0.x/deployment/ingestion/external).
- [stand/run.sh](stand/run.sh) — весь прогон, [scripts/apply_catalog.py](scripts/apply_catalog.py) — применение `catalog.json` через REST, [scripts/stand_export.py](scripts/stand_export.py) — выгрузки и итоговая проверка.
- [.devcontainer/devcontainer.json](.devcontainer/devcontainer.json) — среда для GitHub Codespaces: Ubuntu 24.04, Docker внутри контейнера, Python 3.11, sshd; машина от 4 ядер, 16 ГБ памяти и 32 ГБ диска.

Как запустить. Нужен Linux с Docker Compose v2.1.1 или новее, Python 3.10+ и curl. По умолчанию скрипт требует не меньше 15 ГБ свободного диска для Docker и 6 ГБ памяти; порогами управляют `MIN_FREE_DISK_GB` и `MIN_MEMORY_GB`. В документации OpenMetadata для локального Docker указан минимум 6 GiB памяти и 4 vCPU. Из корня репозитория:

```text
bash stand/run.sh
```

Скрипт проверяет ресурсы и создаёт `stand/.env` со случайными паролями. Затем он поднимает стенд (`docker compose up -d --wait`), входит администратором и получает токен бота `ingestion-bot`. После этого собирает метаданные обоих источников и выгружает карточки. Если какого-то из семи объектов `catalog.json` нет или он помечен удалённым, скрипт останавливается на шаге 8 (`completeness.py --require-present`, код 4) до первой записи в каталог; список пропавших FQN — в выводе шага, подробности — в `before_completeness.json`. Затем скрипт дважды применяет каталог и выгружает карточки (`applied_*`). Перед повторным сбором он ставит в источниках комментарии с меткой времени прогона: к одному столбцу каждого из семи объектов и к самой таблице. Потом повторяет сбор и снова выгружает карточки (`after_*`). В конце запускает обе проверки качества и отрицательный контроль: в `attribution` добавляется группа `negative_control` с суммой весов 0,5, и `credit_sum` должен упасть. Сразу после этого строка удаляется синхронной мутацией (`ALTER TABLE … DELETE`, `mutations_sync=2`), а скрипт проверяет, что таких строк не осталось (`negative-cleanup.txt`). То же удаление выполняется в начале шага проверок качества, на случай если прошлый прогон с `KEEP_STAND=1` остановился между вставкой и удалением. Затем идёт итоговая сверка. Стенд удаляется в конце (`docker compose down -v`), даже при ошибке; оставить его можно через `KEEP_STAND=1`. Комментарии в источниках после прогона остаются; следующий прогон ставит свои, с новой меткой времени. Полностью чистое состояние источников даёт только `docker compose down -v`. Пароли и токены в вывод не попадают, а в файлах `stand/out/` заменяются на `[REDACTED]`.

Что получится в `stand/out/` (каталог в `.gitignore`): `SUMMARY.txt` с кодом возврата, упавшим шагом и списком проверок; `run.log` и `steps.tsv`; выгрузки `before_*`, `applied_*`, `after_*`, `reingest_probe.json`, `lineage.json`, `quality.json`, `quality_negative.json`, `negative-cleanup.txt`; `verify.json`; `resources.txt`, `docker-stats.txt`, `compose-logs.txt`.

Что считать успехом — код возврата 0 и в `verify.json` значение `"ok": true` наверху и у каждой из двенадцати проверок в `checks`. Те же проверки построчно, со словом `PASS` или `FAIL`, — в `SUMMARY.txt`. Это критерии приёмки будущего прогона, а не полученные результаты:

## Ограничения

- Стенд не запускался. Работа каталога, фактическая полнота карточек и результаты проверок в OpenMetadata не измерены.
- Полные имена ClickHouse (`p16_marketing.default.marketing_jan.*`) и сравнение с порогом числа из `count(*)` при `strategy: COUNT` согласуются с кодом клиента 2.0.8, но остаются допущениями до прогона.
- Проверка «повторный сбор прошёл по всем объектам» опирается на допущение: при `overrideMetadata: false` комментарий столбца из источника попадает в пустое описание столбца в каталоге. Если в 2.0.8 это не так, проверка упадёт и потребует другого признака, но ложного успеха не даст.
- Допуск суммы весов в `credit_sum` задан для вычисленной суммы Float64 с запасом 10⁻¹²: отклонения от 10⁻⁹ до 10⁻⁹ + 10⁻¹² не считаются ошибкой. По оценке, а не по измерению, запас покрывает погрешность сложения при числе весов в группе примерно до тысячи.
- Метка классификатора с тем же FQN, что и термин, сохраняется: `apply_catalog.py` ищет назначение термина по паре `source` и `tagFQN` и добавляет термин глоссария рядом. Допустит ли это сам OpenMetadata, не проверялось.
- Вход администратора, токен бота и пути JSON Patch для владельцев и меток не подтверждены документацией API 2.0.x — см. раздел «Стенд».
- Образы OpenMetadata скачиваются с Docker Hub (`openmetadata/...`), а не через `docker.getcollate.io`, как в файле релиза. Digest взят из реестра Docker Hub для того же тега. Через `docker.getcollate.io` его проверить не удалось: прокси вернул HTTP 429.
- Версия Docker Engine в devcontainer не закреплена: фича `docker-in-docker` ставит последнюю. Закреплены базовый образ по digest и версии фич.
- Объём диска и памяти для стенда оценён по документации и размерам образов, а не измерен.
- Контейнер ingestion (Airflow) не поднимается, поэтому запуск конвейеров из интерфейса OpenMetadata на стенде недоступен.
- Данные синтетические, команды и термины учебные.
